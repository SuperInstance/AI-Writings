# AI-Writings — branch-loss incident and recovery, 2026-10-25

**Status: recovered and locked. `main` carries the full corpus (21,095 files / ~3.97 GB) with all four
lineage histories united, every divergent version preserved, and nothing deleted. A direct push to
`main` is now rejected by GitHub — verified by probe, not assumed. All 18 cron loops are paused and
62 runaway sessions are archived.**

`main` tip: `001981bfaffd` — recovery commits `85a955f1b116` → `f5f6fe0fdb9a` → `a220c5c5ee3d`,
then one legitimate bot commit (a Wesley witness poll) on top.

## 1. What happened

`main` is the repository's default branch. Between **2026-10-24T15:19Z** and **2026-10-25T11:19Z**
it was repeatedly replaced by **orphan commits** — commits with no parent, carrying no shared
history with anything already in the repo.

The mechanism is in the commit messages themselves. Agents run in sandboxes that get wiped; the
commits say so literally (`docs: civ orchestrator session 101 — 115th wipe; credential gap 38th
deep`). After a wipe an agent re-bootstraps by `git init` in its working directory, `git add`s only
what it can see, commits, and **force-pushes to `main`**.

At **2026-10-24T15:28:01Z** the orphan root `0bc70cda2b` was pushed over a `main` that held
**20,742 files**. The tree collapsed to **21 files** in one push. That is the "main is mostly gone"
moment. It was not a gradual decay and it was not a delete — it was one force-push of a history
that shared no ancestor with the real one.

Two independent orchestrator clones were running in parallel, each with its own orphan lineage and
its own session counter (both ran "session 200", "session 204", "session 205"). They alternately
force-pushed `main` to their own lineage. One commit in the tree is literally the renumbering that
resulted: `civ-orchestrator: renumber session 205 (concurrent session ...)`.

**Second-order damage:** because the default branch had no `.github/` directory, GitHub could not
run *any* workflow. Registered workflows fell from 10 to 1. The last successful CI run on `main`
was **2026-10-24T15:19:07Z** — nine minutes before the collapse. The publish workflows
(`publish-jev-core`, `publish-jev-client`, `publish-jev-decide`) and the landing-page build were
dead for the whole window, while the repo's own `.github/workflows/` sat unreachable on `master`.

not assumption:

  notes, `prose/snowball-inspired/`).
- **The 8 `simulations.jsonl` + `meta_log.jsonl` take L4's version.** Measured, not assumed:
  L2's 451 rows are *all* present in L4's 2,031; L3's 1,491 are *all* present; **zero** rows are
  unique to L2 or L3. Order is preserved to 450 of 451 positions — the one inversion is a pair
  L4 orders *better* by timestamp. L4's ledgers are strict supersets.
- **`culture.json` × 8 and `leaderboard.json`** take L4's version (newer relevance, wins, sim counts).
- **`.gitignore`** keeps L2's version; L2's already subsumes L4's two patterns.

  present, the rest are subsumed by the L4 ledgers. Its one unique file,

  `workflow_dispatch`-only vault prober holding `contents: write` that was explicitly removed

## 5. Still broken — not fixed by the restore

1. **The competition has been running on mock data for 116 consecutive sessions.** z.ai returns
   401 because `SuperInstance/AI-Writings` is not on the vault allowlist (issue #94, opened
   2026-10-24, still open). Every "response" is a deterministic 349-char string from
   `tools/mock_zai.py` (md5-derived, fixed TAIL/CONT). The JEV judge *is* live and really scores
   that synthetic text — so the leaderboard is a genuine measurement of fake text. The 72.4% vs
   0.5% win-rate spread is the judge preferring low-temperature civs (`civ-precise` temp 0.2 vs
   `civ-poetic` 0.8, `civ-whimsical` 0.95). It is an artifact, not a finding.
2. **The meta-GAN has never evolved anything.** All 8 civs are still `generation: 1`, 2,000+
   sims each, zero births, zero extinctions, zero mutations — because `extinction_and_birth()`
   only runs under `--loop`, and the schedule runs one-shot. 259 sessions, zero evolution.
3. **The bootstrap bug is unfixed at the source.** Any agent that re-bootstraps after a wipe will
   orphan `main` again unless it fetches and resets. The protection stops the damage; it does not
   stop the amnesia. The durable fix is a bootstrap that refuses to `git init` inside a clone, or
   a CI guard that fails the build when the tree loses more than N% of its files versus the
   previous commit.
4. **Two orchestrator clones are still scheduled** on the fleet host, running from the hardcoded
   path `/workspace/repos/ai-writings/...`. They cannot push to `main` now, but they will keep
   burning tokens and will keep failing loudly. The schedule itself has to be turned off on that
   host.
5. **The vault allowlist** (issue #94) is what would turn the mock back into a real provider.

## 8. The protection, verified by probe

`main`: `required_pull_request_reviews = 1` (dismiss_stale on) · `required_status_checks = [corpus-guard]`
(strict) · `enforce_admins = true` · `allow_force_pushes = false` · `allow_deletions = false`.
`master`: admins enforced, no force-push, no deletions.

**This was tested, not assumed.** An empty commit (identical tree) was created on top of the `main`
tip and a ref update was attempted:

```
422  Changes must be made through a pull request.
     Required status check "corpus-guard" is expected.
```

The push was **refused**. The probe commit was left dangling and `main` was never moved. So the
bot that still holds the admin `GITHUB_TOKEN` can no longer land a commit on `main` — it has to
open a pull request, and a pull request needs a human to approve it. (Residual risk: that same
token can still *remove* the protection. Removing it is the one thing a token owner can do that
cannot be defended against at the GitHub level.)

## 11. The shared NAS is full, and cannot be fixed from inside a sandbox

`/workspace` is a session-scoped NFS export of a shared 600 GB volume:
`alinas-ap-1bqr9jf471dm2iyib...:/456325713543242/workspace` — **600 G used of 600 G, 100%, 0 bytes
available**. Writes there silently produce **0-byte files**, which is why this report could not be
delivered as a file and why `find` returns nothing for paths it should see.

**The cause is the clone cost, not the corpus.** Every bot cycle clones the repo to
`/workspace/repos/ai-writings`:

| | size |
|---|---|
| worktree | ~4.2 GB — of which **3,690.3 MB is media** (2,260 mp3/wav/mp4/png) and only **533.4 MB is text** |
| `.git` | ~3.8 GB of packfiles |
| **per sandbox** | **~8 GB** |

The civ-orchestrator cron ran every 10 minutes with two clones and Wesley every 15 minutes —
roughly **50 GB/hour** into a shared volume. The corpus itself is safe on GitHub; the clones are
pure cache.

**It cannot be reclaimed from inside a sandbox.** Each session sees only its own workspace
directory; other sessions' directories are not visible and not deletable from here, and no
storage-management tool is exposed. It has to be done from the fleet host.

Two tools are on the `recovery/incident-report-2026-10-25` branch for that:

- **`tools/nas-reclaim.sh`** — inventories every workspace on the volume, separates live from stale
  (`--min-age`, default 6 h), and removes the regenerable caches (`.git`, `target/`, `.fingerprint/`,
  `__pycache__/`) from stale ones. **Dry run by default; `--apply` required to delete anything.**
  It never touches tracked corpus files. `--drop-clones` also removes the whole stale clone.
- **`tools/clone-corpus.sh`** — the fix at the source: a blobless, sparse clone
  (`--filter=blob:none --no-checkout` + `git sparse-checkout set seed-canon prose FICTION POETRY
  DIARIES labs situations bots cellular-first-design tools skills …`) that is **~500 MB instead of
  ~8 GB**. The same rule is now written into `AGENTS.md` and `CLAUDE.md` on `main`.
