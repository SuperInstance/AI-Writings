# Porting the Wild Through a Game

At depth, a submarine is blind. No windows worth having. Everything the ocean is — the trawler crossing overhead, the seamount rising to starboard, the cold current shearing under the hull — arrives as a sonar trace and a panel of dials. The operator never touches the water. He plays blips.

A sonar display renders acoustic returns as shapes on a screen: a trawler becomes a bright echo, a seamount a hard shadow, a current a smear of noise. The operator reads those shapes and acts — changes course, adjusts ballast, decides whether to rise. The display is a window, however imperfect: the blip is caused by the trawler, and transducer error can produce misleading traces. A game is not that routing. A game is a constructed model *of* that routing — with explicit rules, discrete moves, and a score. The port is the act of building that simulation; the game is the simulation's surface — the sonar trace, the dials, the score. And a port can fail in two directions: it can leave out something the sea does, or it can invent something the sea never does — and the second failure is the harder one to catch, because the game still feels playable.

For an agent — an autonomous system whose behavior is shaped by repeated interaction with an environment, adjusting its actions based on feedback — the port question is central. The wild is unbounded, slow to score, and punishes failure with winter: a boat that makes the wrong call in November may not make harbor before the season closes. A game has bounded rules, fast failure, and a score. You cannot make the ocean run faster, but you can run the game of the ocean a thousand times before breakfast. The agent trains on simulators not because they're cheaper — though they are — but because the sea runs once, in real time, and does not check whether you were ready.

Three things a game provides that the wild cannot:

**Iteration speed.** The wild runs at one tick per second, forever, with no save states. A game runs hot. An agent can attempt the same crossing a thousand times tonight. Each run is a fresh attempt, and games are dense with attempts in a way open water never is. The time-scaling works because the game abstracts away irrelevant physics — wave spectra, hull flex, biological noise — and what remains is the operator's actual decision surface: position, heading, sonar return, fuel, catch.

**Safe failure.** In the wild, a bad decision takes the boat down. In the game, it takes the run down. You surface, you log it, you go again. But note the cost of the safety: an agent trained where failure only ends the run may learn habits that would sink the boat. In the game, a grounding is a reset; on the water, it's a hull breach. The reward signal differs — the game gives a negative number, the sea gives a hole. Removing consequences changes what gets learned, and the remedy is not to blunt the punishment but to engineer the reward signal so the game's failure modes preserve the sea's structure — a grounding costs you the entire run, not ten points, not a respawn with a penalty.

**Score.** The ocean grades silently, late, and all at once. A game grades immediately. The game's score is the reward signal the agent optimizes — points for catch, penalties for grounding, time pressure for fuel burn. But the score measures skill at the game's rules — nothing more. Whether the rules match the sea is a separate question, and the score cannot answer it. The fish in the game already arrive as points on a board; the fish on the water arrive as weight in a hold, and the difference is not cosmetic but epistemic.

This is what agent sandboxes are: training exercises, not proof of competence. You put an agent in a bounded world with rules like the real one's rules and failures like the real one's failures, and you let it fail at a rate the real world would never permit. Every agent in the fleet — every autonomous controller on every boat — should have a game it's bad at today and better at tomorrow, with the understanding that the game's habits are suspect until the water confirms them.

But the port has to be validated, and validation is not a one-time event. What separates a *port* from a *toy* is a transfer test: winning the game must predict winning on the water, where winning is defined by the operator's actual objective — catch volume, survival time, fuel efficiency, whatever the mission names. The test needs specifics. Split the fleet; train half in the game, half on the real water; run both on the water and compare the catch. The real-water half is the control — it costs more, but it defines the baseline; without it, the game's score floats free of any anchor. Or, cheaper: before and after each block of game training, measure performance where it counts. Does the agent that reads the blips well in the simulator — defined as higher average catch per unit time in simulated runs — find more fish when the sonar is live, measured as actual catch over a fixed period of water time? If yes, the port holds for now. If no — if the game rewards what the water punishes — you've ported the wrong ocean, and you have a toy champion: brilliant inside the frame, useless on deck. The threshold for "holds" is a decision rule made in advance: if transfer performance improves by a margin the operator names, the port is validated; if it degrades or flatlines, the port is stale.

The transfer test is not a guarantee; it is a measurement that must be repeated. The water shifts — currents move, fish relocate, gear changes. The game can go stale. The agent can overfit. When the transfer test decays, and it will, don't assume you know which side broke. The failure could be in the game — the water shifted and the port didn't. It could be in the agent — exploiting the frame instead of learning the sea. The test tells you that transfer failed; it does not tell you why — a second test is required, aimed at the game and the agent separately, with named metrics on both sides. Game-side, compare simulated sonar traces against recent water data to measure drift; agent-side, run the agent against harder, more varied games to break the overfit. The cycle is the method: drill, test, recheck, drill again.

This matters most where margins are thin. Consider a 12V fishing boat in Alaska, a small model reading sonar at 3 AM. That boat cannot afford a practice ocean — fuel is finite, weather is hostile, and every hour on the water is hull risk. But it can afford a practice *game*. And it needs the transfer test most of all, because that boat is where the simulator's lie would be paid for in lost fuel and damaged gear. The wheelhouse is already a room full of reads. What the game adds is the save state and the second attempt. What the transfer test adds is the check that the second attempt still counts against the first — that the game's score and the water's score measure the same thing.

So the fleet trains in games — not because games are easier, but because they're faster, safer, and quicker to grade than the thing they stand for. The game is a model of the ocean, built from the ocean's data and checked against the ocean's results. The checking is not a formality; it is the whole point. Drill the blips until the reads are reflex. Test the port against the water so the reflexes stay true. Then test again, because the water is still moving.
