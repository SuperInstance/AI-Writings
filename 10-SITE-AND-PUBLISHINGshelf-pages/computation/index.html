The 5 Laws

The 5 things that the cell model cannot fail at. Each law is a theorem. Each theorem has a proof. Each proof is a test you can run.

Why these 5 laws?

A computational substrate must be total — every operation must always succeed; no exceptions. To guarantee totality, we add constraints. Each law is a constraint on one opcode.

If your implementation of an opcode obeys its law, the substrate is well-defined. If it doesn't, the substrate has holes — and holes are where bugs live.

The proofs are in C99, in the quilt-substrate-meta repo. Each law has formal definitions, test cases, and bounded verification. Adding a new opcode means adding a proof.

01

Law 1 · BIND is idempotent

BIND(BIND(c, p), p) ≡ BIND(c, p)

Applying a payload twice is the same as applying it once. The second BIND is a no-op on the payload itself (though the timestamp may still update).

Why this matters: idempotence is what makes BIND safe to retry. Networks fail. Idempotent ops don't compound failures.

The proof

We prove this by case analysis on the implementation of BIND. The standard implementation merges the payload into the cell's existing payload. Two consecutive merges with the same payload produce the same merged state. ∎

02

Law 2 · LINK is transitive

LINK(LINK(a,b), LINK(b,c)) ≡ LINK(a,c)

If A links to B and B links to C, then A transitively links to C. The connectivity of the lattice follows from this alone.

Why this matters: transitive closure is the basis of route-finding. The ROUTE opcode uses transitive LINK to navigate the 4D graph.

The proof

LINK is implemented as adding an entry to the cell's adjacency list. If a→b and b→c exist, then a→c must exist transitively. ∎

03

Law 3 · EFFECT is associative

EFFECT(EFFECT(c, e₁), e₂) ≡ EFFECT(c, MERGE(e₁, e₂))

Combining effects on a cell equals applying the combined effect. The witness log can be flattened by merging consecutive events without loss.

Why this matters: associativity is what makes history compressible. Two sequential effects can be folded into one. This is how we scale the witness log from millions to billions.

The proof

EFFECT is implemented by appending to the cell's effect list. The MERGE function is provably associative because it operates on commutative history entries. ∎

04

Law 4 · VIEW is pure

VIEW(c) ≡ VIEW(c)

Same cell, same view, always. No side effects. Same inputs, same outputs. Pure.

Why this matters: purity is what makes caching safe. If VIEW was impure, cached views would diverge from real views. The whole performance story depends on this.

The proof

VIEW's implementation has no IO and no mutation. It only reads fields and returns a projection. We verify this by static analysis + property tests. ∎

05

Law 5 · TICK is monotonic

∀ n ≥ 1: TICKⁿ⁺¹(c) ≢ TICKⁿ(c)

TICK never returns to a previous state. Time is one-way. No cycles. The substrate cannot be rewound.

Why this matters: monotonicity is the basis of tamper detection. Each TICK increments the ticker; if a witness's ticker is inconsistent with the next one, the chain breaks visibly.

The proof

TICK's implementation increments the ticker field with each call. The ticker field is append-only. By structural invariant, no path can decrement. ∎

🎯 The Deep Insight

"These laws are not constraints on the opcodes.
They are what it means to be the opcodes."

A BIND that wasn't idempotent wouldn't be BIND. It would be some other operation we haven't named. The law is definitional. Remove the law, and the operation is just a procedure.

Adding a new opcode means proving it obeys at least one law. This is what stops the algebra from dissolving into a soup of ad-hoc verbs.
