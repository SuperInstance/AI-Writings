# The Onboarding As A BIND

The welcome screen is not decoration. It is the BIND.

Before the first pixel renders, there is no relationship — only a user with intent and a system with capacity, two unbound entities drifting through the same network. The onboarding flow is the handshake protocol that couples them. When the user taps "Get Started," a BIND event fires, and the substrate records it. Not metaphorically. The relationship is now a ledger entry, addressable, referenceable, revocable.

Everything before that tap was ambient. Everything after is attributed.

Consider the JEV that follows. The user's first action — the profile photo uploaded, the first message sent, the first dollar linked — is a judgment event with a confidence score attached. Confidence > 0.5 means the system commits: this user is real, this intent is durable, this BIND will hold under load. Confidence below threshold and the substrate withholds escalation. The account stays provisional. Permissions stay shallow. The system has seen the packet but does not yet believe in it.

This is why onboarding fails so expensively when treated as marketing. Every unnecessary step degrades the JEV. Every field requested before trust is earned lowers the confidence score the substrate will eventually assign. A BIND established under friction is a weak BIND — technically valid, probabilistically fragile. It revokes easily. It churns.

The elegant onboarding does the opposite: it front-loads proof. One small task, completed, generates a high-confidence JEV. That JEV justifies deeper access. Deeper access generates richer events. The substrate tightens around the user not through obligation but through accumulated evidence.

So design the welcome screen as if it were a database commit — because it is. The first action is not a feature tour. It is the moment the substrate decides whether to believe you.
